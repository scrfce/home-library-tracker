# Стандарты кодирования проекта «ДомБиблиотека»

Документ действует для всего исходного кода проекта (язык Python 3.12). За соблюдение отвечает разработчик проекта. Основа — PEP 8 и PEP 257 с уточнениями ниже.

## 1. Единый стиль оформления

- Кодировка файлов — UTF-8, переводы строк — LF, отступ — 4 пробела, табуляция не используется.
- Максимальная длина строки — 100 символов.
- Строки в двойных кавычках `"..."`.
- Форматирование и проверка выполняются инструментом **ruff** (настройки в `pyproject.toml`): `ruff format .` и `ruff check .`. Код с замечаниями линтера в репозиторий не попадает.
- Идентификаторы (имена переменных, функций, классов) пишутся по-английски; комментарии, docstring и сообщения пользователю — по-русски.

## 2. Правила именования

| Элемент | Правило | Пример |
| --- | --- | --- |
| Классы | `PascalCase`, существительное | `CatalogService`, `BookRepository` |
| Исключения | `PascalCase`, суффикс `Error` | `BusinessRuleError` |
| Функции и методы | `snake_case`, глагол | `add_book()`, `list_active_loans()` |
| Переменные и параметры | `snake_case`, понятное имя без сокращений | `due_date`, `borrower_name` |
| Константы | `UPPER_SNAKE_CASE`, только в `config/settings.py` или в начале модуля | `MAX_LOAN_DAYS` |
| Защищённые элементы | префикс `_` | `self._session`, `_register_unicode_lower()` |
| Логические значения | префикс `is_`, `has_`, `can_` | `is_available()`, `is_overdue()` |
| Файлы и пакеты | `snake_case.py`, имя файла отражает содержимое | `loan_service.py`, `repositories.py` |
| Тесты | файл `test_<модуль>.py`, функция `test_<что_проверяем>_<условие>` | `test_cannot_issue_book_twice` |

Запрещены однобуквенные имена (кроме счётчиков циклов `i`, `j`) и неочевидные сокращения.

## 3. Организация файлов и архитектура

Проект разделён на слои согласно диаграмме компонентов; зависимости направлены только сверху вниз:

```
routes (HTTP)  ->  services (бизнес-логика)  ->  models/repositories (данные)
                          \-> utils (ошибки, проверка данных, безопасность)
```

- `src/routes` — только приём запроса и формирование ответа, без бизнес-логики.
- `src/services` — бизнес-правила; один файл — один модуль (`auth_service.py`, `catalog_service.py`, `loan_service.py`). Сервис не знает про HTTP и шаблоны.
- `src/models` — ORM-модели и репозитории. Запросы к БД пишутся **только** здесь.
- `src/utils` — ошибки, проверка данных, безопасность; не зависят от остальных слоёв.
- `config/` — настройки; секретные значения берутся из переменных окружения.
- Один класс — одна ответственность (SRP); файл не должен превышать ~300 строк.
- Порядок импортов: стандартная библиотека, сторонние пакеты, модули проекта (ruff расставляет автоматически).

## 4. Оформление функций и методов

- Функция решает одну задачу; длина — не более 40 строк, параметров — не более 7 (для большего числа используются именованные аргументы).
- Для всех публичных функций обязательны аннотации типов параметров и результата.
- Публичные функции имеют docstring в формате PEP 257 на русском: краткое описание, при необходимости разделы `Args`, `Returns`, `Raises`.
- Побочные эффекты (запись в БД, изменение статуса) явно указываются в описании и выполняются в сервисе, а не в модели.
- Изменяемые значения по умолчанию (`[]`, `{}`) не используются.

## 5. Комментарии

- Комментарий объясняет **почему** так сделано, а не пересказывает код.
- Устаревший и закомментированный код удаляется (история хранится в Git).
- Для незавершённых мест используется `TODO(день N): что сделать`.
- Модуль начинается с docstring: назначение и связанные требования (FR/NFR).

## 6. Обработка ошибок

- Сервисы выбрасывают только исключения из `src/utils/errors.py`: `ValidationError`, `AuthenticationError`, `AccessDeniedError`, `NotFoundError`, `BusinessRuleError`.
- Запрещены «голые» `except:` и пустой `except ...: pass`. Перехватывается конкретное исключение.
- Все входные данные проверяются на границе сервиса до обращения к базе данных (`src/utils/validation.py`).
- Сообщения об ошибках понятны пользователю и не раскрывают внутреннее устройство (например, при входе не сообщается, существует ли email).
- Изменения в БД фиксируются (`commit`) только после успешной проверки всех условий; при ошибке данные не меняются.

## 7. Работа с Git

- Основная ветка — `main`; крупные изменения выполняются в отдельных ветках `feature/<описание>`.
- Один коммит — одно логически завершённое изменение; перед коммитом запускаются тесты (`python -m pytest`) и `ruff check .`.
- Сообщения коммитов по схеме Conventional Commits: `тип: краткое описание в повелительном наклонении`.

| Тип | Назначение | Пример |
| --- | --- | --- |
| `feat` | новая функциональность | `feat: implement loan service` |
| `fix` | исправление ошибки | `fix: make book search case-insensitive for Cyrillic` |
| `docs` | документация | `docs: add coding standards` |
| `test` | тесты | `test: add loan service tests` |
| `refactor` | изменение кода без смены поведения | `refactor: extract ownership check` |
| `chore` | служебные изменения | `chore: add ruff configuration` |

- В репозиторий не попадают временные файлы, базы данных, `.env`, кэши и виртуальные окружения (см. `.gitignore`).

## 8. Требования безопасности

- Пароли хранятся только в виде хэша PBKDF2-HMAC-SHA256 с уникальной солью (`src/utils/security.py`), сравнение выполняется через `hmac.compare_digest`.
- Пароли, ключи и адреса баз данных не пишутся в код и не попадают в Git: используются переменные окружения и файл `.env`.
- Доступ к данным проверяется на сервере: пользователь работает только с книгами своей библиотеки (`src/services/access.py`).
- Запросы к БД выполняются только через ORM с параметрами; конкатенация SQL-строк запрещена.
- Входные данные считаются недоверенными и проверяются по типу, длине и формату.
- Сообщения об ошибках и журналы не содержат паролей и хэшей.

## 9. Тестирование

- Каждый сервис и функция проверки данных покрываются тестами `pytest` в каталоге `tests/`.
- Тест проверяет одну ситуацию; обязательно проверяются и корректные, и некорректные данные.
- Тесты не зависят друг от друга и работают с чистой базой SQLite в памяти.
- Цель покрытия бизнес-логики — не менее 70 % (NFR-11).
